# PatchLoop

> 日本語版: [README.md](./README.md)

PatchLoop is an experimental prototype for collecting browser-based visual feedback on AI-generated demos and turning that feedback into Slack, GitHub, or AI repair context.

## Run Locally

Serve the folder with any static file server and open `examples/plain-html/`.

```sh
python3 -m http.server 4173
```

```text
http://localhost:4173/examples/plain-html/
```

## Development

Node.js 22.x from 22.13.0, or 23.4.0 or later, is required (the receiver uses `node:sqlite` and loads the shared ES module via `require()`). CI checks the minimum supported version, 22.13.0, and the development runtime, 24.x.

Install dependencies.

```sh
npm install
```

Run lint and tests.

```sh
npm run lint
npm test
npm run check
```

`npm test` uses the Node.js test runner to start the local receiver on a temporary port and verify `/feedback` and `/import` storage, validation, and screenshot handling. Test data is created under the OS temp directory and removed after each test.

GitHub Actions (`.github/workflows/check.yml`) runs the same `npm run check` on pushes to `main` and on every pull request.

The widget source lives in `widget/src/` as ES modules; the distributable single file `dist/patchloop-widget.js` is generated by a dependency-free build script. `dist/` is committed, and `npm run check` verifies it matches a fresh build.

```sh
npm run build
```

When the receiver is running, the same bundle is also served at `http://localhost:4000/widget.js`.

Check by hand that the widget is isolated from page CSS with `examples/page-css-isolation/`: run `python3 -m http.server 4173` at the repo root, open `http://localhost:4173/examples/page-css-isolation/`, and confirm that toggling the rules does not change the widget (the closed button, the open panel, the selection-mode guide, the comment form, pins and areas, the sent list, and the delivery settings).

## What Works Now

script-tag widget:

- Compact panel opened with the bottom-right Feedback button
- Add-comment action with a page selection guide and an explicit exit button
- Click-to-pin location capture and drag-to-select area capture
- Draft markers that take their final sequential number on submit
- Comment mode stays active after submit so several spots can be annotated in a row
- Cmd+Enter (Ctrl+Enter on Windows) submits the comment form
- Target element outline while a draft is pending
- Per-feedback comment list with reviewer, kind, comment, and delivery status
- Hover tooltip on markers showing the comment (disabled in feedback mode)
- Activating a marker opens the panel and moves focus to its comment in the list (disabled in feedback mode)
- A "マーカーの表示" (marker display) switch in the panel: normal / dots only / all. Dots only turns sent markers into small dots without numbers or area frames, and shows an area's frame only while its dot is hovered or focused. The choice is saved per origin in `localStorage` under `patchloop:display-mode`. Normal and dots only hide the markers of comments finished in the inbox (fixed or ignored); all shows them gray and dashed
- The inbox status of comments sent to a receiver is looked up with `POST /feedback-status` and shown next to the delivery status in the list (as "受信箱: 修正済み" and so on, or "受信箱に無い" when the answer leaves the comment out). Lookups run on load, when the panel opens and when the tab comes back, at least 30 seconds apart; repeated failures stretch the gap up to 10 minutes, and 401 / 403 / 404 stop them for the page. Only the receiver delivery mode with an `endpoint` whose path ends in `/feedback` looks up. Statuses live in memory only (not in this browser's storage or in exports), nothing is hidden when they cannot be had, and a comment edited here after it was sent is not hidden even when finished in the inbox
- Per-item edit and delete inside the panel with marker renumbering
- Payload with URL, point/area position, selector, viewport, browser, reviewer, and timestamp
- Lightweight viewport screenshot snapshot (SVG) attached to each payload
- `localStorage` persistence for the feedback list, including pin / area overlay restoration after reload
- Markers re-anchor to their target element (via selector) on window resize, following layout reflows
- When re-anchoring fails (element missing, hidden or of no size), markers go back to their stored position with an approximate badge (≈, “対象の要素が見つからないため、保存した位置に表示しています”, i.e. the element was not found). For pages that draw their content after loading, a marker whose element is missing is tried again three times over the first 3 seconds, and the badge goes once the element is found. A comment made where there is no element to anchor to (on an element larger than the viewport, for example) gets the badge (“ウィンドウサイズが変わったため、位置が近似になっています”) only when the window size differs from when it was made
- Optional `onSubmit(payload)` callback
- Optional `endpoint` setting that POSTs payloads to the bundled local receiver
- Optional Slack Incoming Webhook forwarding from the local receiver with screenshot links, image blocks, and optional file upload
- Download mode that batches the unsent feedback of every page of a project / demo saved on this device into one versioned JSON bundle (tracked with an `exported` flag)
- Receiver inbox import for download-mode bundles (both single and batch)
- Configurable delivery mode for receiver forwarding, direct Slack webhook delivery, download, or no delivery

## Embeddable Widget

PatchLoop includes a standalone widget that can be embedded into a normal HTML page with a `script` tag.

```html
<script src="../../dist/patchloop-widget.js"></script>
<script>
  window.PatchLoop.init({
    projectId: "patchloop",
    demoId: "plain-html-renewal-review",
    endpoint: "http://localhost:4000/feedback",
    showDeliverySettings: true,
    onSubmit(payload) {
      console.log(payload);
    }
  });
</script>
```

### Supported Environments

The widget supports desktop Chrome and Edge (both on the latest stable release). It is tested on Chrome. Edge runs the same engine as Chrome (Chromium), so it is included, but it has not been tested on Edge itself yet.

| Browser | Status |
| --- | --- |
| Desktop Chrome / Edge | Supported |
| Safari / Firefox | Untested |
| Phone and tablet browsers | Untested |

The widget may work in untested environments, but they have not been checked. Known differences: Safari 16.3 and earlier cannot read the regular expression lookbehind in the widget code, so the whole widget fails to load. How screenshots come out was checked on Chrome and may differ in other browsers (see "What Screenshots Do Not Capture").

| Input | What it can do |
| --- | --- |
| Mouse | Select a point (click) or an area (drag). Hovering a marker shows its comment |
| Keyboard | Tab to a button, link or other control on the page and press Enter to select the center of that element as a point (areas cannot be selected). Tabbing to a marker shows its comment, and Enter moves to that comment in the list |
| Touch | Untested. A tap selects a point. Moving the finger cancels the selection and scrolls the page, so areas cannot be selected |

Marker names, tooltips on focus, Escape to cancel with focus restored, and text contrast (4.5:1 or more) are covered by tests. It has not been checked with a screen reader yet.

### Init options

- `projectId` (string) — project identifier carried in the payload; defaults to `local-demo`. When the receiver binds the ingest key to a projectId, pass the same `projectId` to the widget too (the widget sends the default `local-demo` when none is given, and the key's projectId does not fill it in, so posts are refused with `403` when that differs from the key's projectId)
- `demoId` (string) — demo identifier carried in the payload; defaults to `plain-html`
- `sourceContext` (object, optional) — git provenance of the page under review: `{ repo, branch, commit, root, buildUrl, previewUrl }`, all optional strings. The embedding side injects real values at build/deploy time; this is what lets an AI agent map feedback back to source code. Fields left unset are filled from `<meta name="patchloop:repo">` / `patchloop:branch` / `patchloop:commit` / `patchloop:root` / `patchloop:build-url` / `patchloop:preview-url` meta tags. `buildUrl` and `previewUrl` leave under the same rule as `page.url` (the fragment and any credentials dropped, only the query keys listed in `keepQueryParams` kept; a relative URL keeps its path and those keys, and a value that starts with a scheme or `//` (or `\\`) but does not parse becomes empty, judged as the URL parser reads it: tabs and newlines removed, spaces trimmed from the ends), so a preview share token passed in the query does not leave the browser
- `keepQueryParams` (string[], optional) — query keys to keep in the payload's `page.url`. Defaults to `[]`: `page.url` is origin + path only, and the query, the fragment (after `#`), and any credentials in the URL are dropped. For an app that keeps screen state in the query, list the keys needed to reproduce it (for example `"step"` for `?step=`); only those pairs are kept, in their original order and with their original values (keys match case-sensitively; the fragment is always dropped). Kept values reach the inbox, Slack, GitHub issues, and exported files as-is, so do not list a key that may carry a token or another secret; that is the embedding side's responsibility. A non-array value, or an element that is not a non-empty string, is ignored with a console warning, and no query is kept for it. The current setting is applied again on every send, retry, and export, and comments already saved on the device have their `page.url` trimmed by it when loaded and are saved back, so only what the current setting keeps ever leaves the browser. The receiver does not trim the `page.url` it receives
- `reviewer` (string, optional) — pre-fills the reviewer field in the comment form. When omitted, the widget restores a saved reviewer from `localStorage`; otherwise the field starts empty
- `reviewerStorageKey` (string, optional) — `localStorage` key used to persist the reviewer name; defaults to `patchloop:reviewer`
- `maxFieldLength` (number, optional) — the longest comment and reviewer name, counted as they are saved (without leading and trailing whitespace) and, like the receiver, in JavaScript `string.length`. Defaults to `20000`, the receiver's default `maxFieldLength` / `MAX_FIELD_LENGTH`. Past it, the field shows its length below it while typing and the comment cannot be confirmed. A comment saved on the device that is past it (after lowering the limit, for example) is neither resent nor exported, and the widget asks to shorten it by editing (an export writes out the others). When you change the receiver's limit, set the same value here: keeping them aligned is the embedding side's responsibility. With a larger value here, the receiver refuses what is past its limit with `413`, and an exported file with even one such comment is refused as a whole on import. A value that is not a positive integer is reported in the console and the default is used
- `persistFeedback` (boolean, optional) — save the feedback list to `localStorage` and restore it after reloads on the same project / demo / page URL; defaults to `true`
- `feedbackStorageKey` (string, optional) — namespace for the `localStorage` keys used to persist feedback; defaults to `patchloop:feedback`. Storage is separated by this value, project, demo, and the page's origin + pathname (query strings and hashes identify the same page). Legacy single-key data migrates only when its scope matches; it is retained if copying to the new key fails
- `deliveryMode` (`"receiver"` | `"slack-webhook"` | `"download"` | `"none"`, optional) — delivery target; defaults to `"receiver"`
- `endpoint` (string, optional) — URL the widget POSTs each payload to; nothing is sent when omitted
- `ingestKey` (string, optional) — per-project public key sent to the receiver in the `X-PatchLoop-Ingest-Key` header; required when the receiver sets `INGEST_KEYS` / `ingestKeys`. It is embedded in the page, so it is not a secret — it identifies the project, deters indiscriminate spam, and can be rotated to revoke
- `slackWebhookUrl` (string, optional) — Slack Incoming Webhook URL used when `deliveryMode: "slack-webhook"`
- `showDeliverySettings` (boolean, optional) — show the delivery target controls in the panel; defaults to `false`
- `captureScreenshot` (boolean, optional) — include a viewport snapshot in the payload; defaults to `true`
- `screenshotMaxBytes` (number, optional) — widget-side byte limit before omitting the snapshot; defaults to `1200000`
- `onSubmit(payload)` (function, optional) — called on every submit. Synchronous exceptions and rejections from a returned Promise are reported in the console; receiver / Slack delivery continues independently of the callback's success or completion

### window.PatchLoop API

- `PatchLoop.init(options)` — mount the widget and start capturing
- `PatchLoop.destroy()` — remove the widget DOM, markers, and highlights, and cancel initialization waiting for DOM readiness. If `init()` is called repeatedly before the body exists, only the latest options are used
- `PatchLoop.setFeedbackMode(boolean)` — toggle comment mode programmatically
- `PatchLoop.getFeedback()` — return a copy of the current feedback list (newest first)

### Events

`document` dispatches `patchloop:feedback` with `event.detail = payload` whenever a comment is submitted, before any `endpoint` POST resolves.

### Basic flow

1. Open the panel with the bottom-right Feedback button
2. Choose “コメントを追加” (Add comment); the panel collapses and a selection guide appears
3. Click a point or drag an area. On touch screens, tap a point. With a keyboard, Tab to a page control and press Enter
4. Enter a comment and reviewer name; both are required. Submit with the button or Cmd+Enter / Ctrl+Enter. Uncheck “画面画像を含める” to omit the screenshot for this comment
5. Check delivery in the list. Failed requests can be retried after checking connection/settings. Requests time out after 15 seconds without removing the comment. If the same ID has already been received, verify its contents in the inbox
6. End selection with the guide’s exit button or Escape

When the bottom-right Feedback button is in the way of the page, press “›” next to it to tuck it into a small tab (‹) at the right edge of the screen. Press the tab to bring the button back. The choice is kept on this device (`localStorage` key `patchloop:launcher`) and lasts across reloads (only while the page is open in browsers that cannot store it). While tucked, pressing a marker still opens the panel, and closing the panel goes back to the tab.

Deletions affect this browser only, not received feedback or GitHub Issues. Editing a delivered (including one whose ID the inbox already had, and one whose delivery was cut off before its answer) or exported comment makes a revision of it: a new comment with a new ID whose `replaces` holds the original ID, which takes the original’s place in the list and on the page. The revision is delivered at once when there is a destination, or goes into the next export in download mode. The received original and any GitHub Issue made from it are not rewritten. Editing a comment that has not left this browser changes it in place. A comment edited after delivery or export before this change (shown as a local change not yet at the destination) is delivered as a revision when it is edited and saved again, even unchanged. See “What the Image File Holds” for what goes into the image file. Nothing is masked automatically, so omit the image on pages with sensitive information.

The reviewer name is saved to `localStorage` after submit and restored the next time the widget starts. The feedback list is also saved to `localStorage` by default and restored after reloads on the same project / demo / page URL, including pins and area overlays. The panel’s “この端末のコメントを消す” action removes both visible markers and saved feedback from this browser. Tabs open on the same page share one saved list: comments added, edited or deleted in one tab show up in the other tabs’ lists and markers right away, and a save in any tab never overwrites another tab’s comments. When two tabs edit the same comment, the later save wins; a deleted comment (including by “この端末のコメントを消す”) stays deleted even if another tab was editing it. Set `persistFeedback: false` for memory-only behavior.

Tab to a comment marker to read its tooltip, and press Escape to dismiss it. Press Enter to move to its comment in the list. In the comment form, Escape cancels the entry or edit and restores focus to the previous control.

### What the Image File Holds

The screenshot (SVG) file holds a copy of the page body's DOM. Inside elements the page does not render (`display:none`: the `hidden` attribute, `<template>`, a closed `<dialog>`, anything a stylesheet hides that way) and inside elements that do not render their contents (`content-visibility: hidden`, as `hidden="until-found"` gives, when `display` is `block`, `flex`, `grid`, `inline-block`, `table-cell` and the like; with `contents`, `inline`, `table` and so on the contents are rendered and stay; the element's own box and attributes stay), every text becomes one invisible character that keeps only its direction (RLM when the first strong character, the one `dir="auto"` goes by in the browser, is right-to-left, LRM when it is left-to-right, a space when there is none), the attributes that carry content (`value`, `href`, `src`, `srcdoc`, `data`, `title`, `alt`, `placeholder`, `aria-label` and the like) become empty. The contents of every `<template>` go, wherever it is. The elements and their other attributes (`class`, `id`, `data-*`, `type`, …) stay, so the page's selectors (`:empty`, `:nth-child`, `+`, `~`, `:has()`, `[value]`, `:dir()` and so on) match as on the page and `dir="auto"` works out the same direction (only a selector on the value of an emptied attribute could differ). These go in as they are even when not rendered, wherever they are: SVG (a hidden SVG often holds icons that `<use>` draws elsewhere), `<style>` and `<link>` (they style the page), and form values (`<select>` and its options, `<textarea>` contents, the `value` and `placeholder` of an `<input>` other than `type="hidden"`; the form's validity and `:placeholder-shown` can style what is shown, and a `<select>` shows its selected option even when it is hidden). The `value` of an `<input type="hidden">` is emptied. HTML comments are left out, as are `script` elements and the widget itself. Since they affect the layout, parts outside the viewport (further down a scroll), elements hidden by `visibility: hidden`, transparency or overlap, and attributes of shown elements (link targets and so on) go in as they are.

### What Screenshots Do Not Capture

The screenshot copies the page body into an SVG `foreignObject` and draws it as an image; it is not a capture of the browser's screen. As a result, the following are missing from the image or look different from the actual screen. The inbox list thumbnails and images embedded in GitHub Issues are drawn as images, so they look as described here (checked in Chrome; other browsers may differ).

Not captured:

- Shadow DOM contents (open and closed), such as the dev indicator of the Next.js dev server or Web Components
- What is drawn on a `canvas`
- `iframe` / `frame` contents (same-origin and `srcdoc` ones included) and `object` / `embed` contents
- `video` frames
- Images loaded from a URL (an `img` shows as a broken image) and CSS background images loaded from a URL. Data URL images and `svg` written in the page are captured

Captured differently from the screen:

- Web fonts loaded from a URL (drawn in another font)
- Rules from stylesheets loaded from another origin without CORS (their `cssRules` cannot be read, so they do not apply)
- Form state changed after load (typed text, checkbox and `select` choices), which shows in its initial state from the HTML
- The scroll position inside scrollable elements (back at the top)
- When any of the above changes an element's size, the layout after it shifts too. The point / area marks are drawn at the coordinates on the actual screen, so they can look slightly off from the elements in the image

Of these, elements with an open shadow root, `canvas`, `iframe` / `frame`, `object` / `embed` and `video` are detected by the widget and recorded in the payload's `screenshot.uncaptured` (a closed shadow root cannot be detected). Those that touch the selected spot are outlined on the image with a dark dashed frame and a number (their place in `screenshot.uncaptured.regions`, counted from 1). While a comment is written, the form also asks the reviewer to describe what they see when such an element touches the selected spot (when screenshots are taken). The widget's own UI, its markers and `script` elements are left out; the selected spot is drawn as a mark over the image. Opening the image in a new tab from a link in the inbox or a GitHub Issue (the file shown as a document) keeps the same layout, but data URL images do not show and `srcdoc` iframes are drawn (the receiver serves it with a CSP that blocks loads).

## Payload

Main payload fields:

- `id`
- `replaces` — on a revision only: the `id` of the comment it replaces (from `schemaVersion` 4)
- `projectId`
- `demoId`
- `comment`
- `reviewer`
- `page.url` — URL of the page the comment was left on: origin + path plus only the query keys listed in `keepQueryParams` (never the fragment or credentials in the URL)
- `page.title`
- `sourceContext` — git provenance of the reviewed page (`repo` / `branch` / `commit` / `root` / `buildUrl` / `previewUrl`); `null` when neither the init option nor meta tags provide any field
- `target.kind`
- `target.x`
- `target.y`
- `target.clientX`
- `target.clientY`
- `target.pageX`
- `target.pageY`
- `target.documentX`
- `target.documentY`
- `target.area`
- `target.selector`
- `target.text`
- `target.anchor` — position inside the anchor element rect (percent) plus its `selector`; includes `width` / `height` for areas. Used to re-anchor markers on resize and reload. Areas anchor to the element under the area's center rather than the drag start. Elements larger than the viewport (`main`, `body`, …) are skipped because relative positions inside them are unstable; such markers keep their page pixels and show the approximate badge (≈) only when the window size differs from when the comment was made
- `environment.viewport`
- `environment.browser`
- `environment.language`
- `screenshot` — viewport snapshot. On success it includes `status: "captured"`, `mimeType: "image/svg+xml"`, `dataUrl`, `targetOverlay`, and related metadata
- `screenshot.uncaptured` — elements in the viewport that the image cannot show (elements with an open shadow root, `canvas`, `iframe` / `frame`, `embed` / `object`, `video`). It has `version`, `status` (`detected`, or `failed` when detection failed), the number of scanned elements `scannedElements` and whether the scan stopped at 20,000 elements `scanTruncated`, per-kind `counts`, and up to 20 `regions` (`kind`, `tag`, viewport rectangles `rects`, and the `relation` to the selected spot). `relation` is `covers-target` when the element is on top at the selected spot, `overlaps-target` when its rectangle meets the spot, and `none` otherwise; beyond 20 regions they are kept in that order. Shadow tree and frame contents are not included. It is present only when the image was captured; a payload without it (from a widget sending `schemaVersion` 2 or earlier) means the detection did not run. The receiver checks the shape of `version` 1 and, when it is malformed, still stores the feedback but replaces this field with `{"version": 1, "status": "invalid"}` (`null` when `version` is not an integer). An unknown `version` is stored as sent
- `createdAt`
- `delivery` — external delivery adds `{ pending: true, target: "receiver" | "slack-webhook" }` before the notification event and `onSubmit` callback. It is replaced with `{ ok, status }` or `{ ok: false, error }` after delivery, plus the text that went out (`sent`: `comment` and `reviewer`) when the receiver may hold it. An edit after delivery normally makes a revision; the list shows a local change not yet at the destination only for comments edited before revisions existed and for those edited in another tab while they were being delivered (whose `sent` differs from the current text). Direct Slack delivery reports `{ ok: null, status: "unknown", target: "slack-webhook" }`. Restoring interrupted delivery produces `{ ok: null, interrupted: true, target }`, meaning the outcome is unknown. A pending `delivery` also records when it started (`startedAt`). Closing or reloading the tab, or `destroy` / `init` again, saves the comments still being delivered as interrupted. A comment another tab is delivering stays pending (with no retry offered) until that tab saves the result or the delivery timeout (15 seconds) plus a margin has passed. These are local delivery states, left out of exported files and not stored in the receiver’s received record

`target.kind` is either `point` or `area`. For area selections, `target.area` carries the viewport percentages (`x` / `y` / `width` / `height`) plus pixel values for `clientX/Y/Width/Height`, `pageX/Y`, and `documentX/Y/Width/Height`.

The `target` coordinates, like `environment.viewport` and the screenshot, record the moment the comment was confirmed. `clientX/clientY` are viewport coordinates at that moment, while `pageX/pageY` are document coordinates including scroll. Pins and area overlays are anchored to document coordinates so they stay attached to the target while scrolling. Inside a box that scrolls within the page, or a canvas moved by a CSS transform (a flow diagram panned with the wheel or a drag, for example), markers are put back on their elements by `target.selector` + `target.anchor` after a scroll, a wheel, a drag or a key (so is the number of the place being commented on). When the element leaves the visible part of a scrolling box (an ancestor whose `overflow` is not `visible`), its pin is hidden and its area overlay shrinks to the part inside (or is hidden when none is); they come back when it returns. When an area is selected, its anchor for this is an element inside the scrolling box or canvas rather than the box itself, so that it moves with the content. Markers whose element cannot be found, and those of elements that escape an ancestor by fixed or absolute positioning, are not followed or cut this way. When a window resize or a reload reflows the layout, markers re-anchor to the target element via `target.selector` + `target.anchor`, but the `target` coordinates are not rewritten (what is saved, sent, and exported stays as confirmed).

### Compatibility

Payloads and export files each carry a version.

| Payload `schemaVersion` | Field added |
| --- | --- |
| 1 (a payload without `schemaVersion`) | — |
| 2 | `sourceContext` |
| 3 | `screenshot.uncaptured` |
| 4 (the current widget) | `replaces` |

| Export file `version` | Shape of `feedback` |
| --- | --- |
| 1 | A single object |
| 2 (the current widget) | An array |

The receiver handles them as follows.

- Payloads of past versions stay accepted. A payload without `schemaVersion`, or with `null`, is stored as version 1. A `schemaVersion` that is not an integer is refused with 400
- A payload of a version newer than the receiver is not refused either. Unknown fields at the top level of the payload are stored as sent. Its card in the inbox says the format is newer than this receiver (unknown fields have no display of their own; they can be checked in the card's "JSON データ" (JSON data))
- Fields the receiver knows are handled as the current receiver handles them, whatever the version: their shape is checked (most fields are refused with 400 when broken, while a broken `screenshot.uncaptured` is replaced with `invalid` and the feedback stored), and the ones the receiver reworks on receipt are reworked. For example, the image data in `screenshot` is saved to a file and replaced, and `screenshot.uncaptured` of `version` 1 keeps only the fields the receiver knows, so unknown fields inside it are not stored
- These fields are not stored even when sent: the ones the receiver owns (`receivedAt`, `received`, `importedAt`, `source`, `statusUpdatedAt`, `integrations`) and the marks used on the device only (`delivery`, `exported`, `exportedAt`, `exportedFileName`, `previousIds`, `localEdited`). `status` always starts as `new` on receipt (an import keeps the value in the export file)
- Stored records are not rewritten when the receiver is updated; they are read into the current shape (for example `screenshot.uncaptured`)
- An export file of an unknown `version` is refused with 400. When it is newer than the receiver, the error says to update the receiver

A field inside the payload may carry its own version: the `version` of `screenshot.uncaptured` (1 for now) is counted apart from `schemaVersion` (see the field's description above).

## Local Receiver

When `endpoint` is set, the widget POSTs the payload to that URL. A local receiver is bundled for testing.

```sh
node server/receive.js
```

- Accepts payload at `POST /feedback`, storing it in `server/feedback.db` (sqlite) by default. The response is only `{"ok": true, "id": "pl_..."}`: the stored count and the result of the Slack notification are not returned (the inbox and the log show them). A refusal says why in `error` (`400` / `403` / `409` / `413` / `507` and so on). A failure of the receiver itself, such as writing the screenshot file or the store, returns `500` with `"Internal Server Error"` only, and its details (server paths and the like) go to the log only
- Imports download-mode JSON bundles at `POST /import` (single v1 feedback or array-based v2 batch), storing them in the same inbox format. Duplicate ids are skipped, and the response returns `imported` / `duplicates` / `failed`
- Renders an inbox of received feedback at `GET /`
- The inbox has text search, project, and status filters, plus detailed filters for kind / demo / reviewer / source / Slack / GitHub
- The sidebar shows counts by status. Search and filters remain in place after actions, with inline success/error messages. Imports show added/duplicate/failed counts before an explicit inbox refresh.
- Each feedback has a triage status (`new` / `accepted` / `fixed` / `ignored`) editable from the card; statuses persist to sqlite
- The card of a revision (feedback with `replaces`) says it revises the original comment, and the card of a replaced feedback says it has revisions, each linking to the other (with the id when the original is not in this inbox). The original is never rewritten and keeps its own status. GitHub Issue bodies and Slack notifications show the original id as `Replaces`
- `POST /feedback/:id/status` updates the status via the API (body: `{"status": "accepted"}`)
- `POST /feedback-status` looks up the status of the comments a widget sent (body: `{"ids": ["pl_..."], "projectId": "..."}`; `projectId` is optional). The response is `{"ok": true, "statuses": [{"id": "pl_...", "status": "fixed"}]}`: unknown ids are left out and no feedback content is returned (`Cache-Control: no-store`). `ids` takes 1 to 200 entries of 1 to 200 characters, in a body of at most 64 KiB (or `MAX_BODY_BYTES` when that is lower). Like `POST /feedback`, it is subject to the origin allowlist, ingest keys (a key bound to a project only sees that project's feedback) and the rate limit. Anyone who knows an id can read its status, so by default a receiver with `RECEIVER_TOKEN` set does not have this endpoint (404; `statusLookup` changes this, see below)
- `DELETE /feedback/:id` removes a feedback and its screenshot (also from the card's delete button)
- With GitHub configured, each inbox card can create a GitHub Issue (see below)
- Imports `.patchloop-feedback.json` files from the inbox UI
- Returns the raw JSON at `GET /feedback.json` (filterable via `?projectId=` / `?demoId=` / `?status=`)
- Serves saved screenshots from `GET /screenshots/:file`
- Liveness monitoring at `GET /healthz` (200 with a store connectivity check; 503 on store failure or during shutdown; no auth required and exempt from rate limiting)
- Graceful shutdown on SIGTERM / SIGINT (stops accepting new connections, waits for in-flight requests and the store to close, then exits; force-exits after 10 seconds)

Deletion returns `200` after removing both the screenshot and the database row. If either deletion fails, it returns `500` and keeps the feedback so the request can be retried. A missing screenshot does not prevent a successful retry. Deletion and GitHub Issue creation for the same feedback share a lock; overlapping requests return `409`.

### Storage

Feedback is stored in the built-in `node:sqlite` (`server/feedback.db`). The backend sits behind a small async interface in `server/store.js` (`init` / `insert` / `get` / `list` / `update` / `updateIntegration` / `delete` / `count`), so it can be swapped for another backend (e.g. MySQL) later without changing the receiver.

On startup, an existing legacy `server/feedback.json` is migrated once into an empty database that has not completed migration, then archived to `feedback.json.migrated-<timestamp>` (or `feedback.json.corrupt-<timestamp>` if unreadable, starting empty). Completion is also recorded in the database, so an archive failure cannot cause old feedback to be imported again after all rows are deleted and the receiver restarts. Existing databases with feedback retain their data and are marked as migrated without importing the legacy JSON. The db path is set via `FEEDBACK_DB_PATH` and the migration source via `FEEDBACK_STORE_PATH`.
- Configurable via `PORT` / `HOST` env (default `127.0.0.1:4000`)
- Configurable sqlite db path via `FEEDBACK_DB_PATH` (`FEEDBACK_STORE_PATH` is the legacy `feedback.json` migration source, not the storage path)
- Configurable screenshot directory via `SCREENSHOT_DIR`
- Configurable receiver URL for Slack links via `PUBLIC_BASE_URL`
- Configurable payload and screenshot limits via `MAX_BODY_BYTES` / `SCREENSHOT_MAX_BYTES`
- Configurable payload shape limits via `MAX_IMPORT_ITEMS` / `MAX_FIELD_LENGTH` / `MAX_ARRAY_LENGTH` / `MAX_OBJECT_DEPTH` (or config `maxImportItems` / `maxFieldLength` / `maxArrayLength` / `maxObjectDepth`): caps the items per `POST /import`, string length, array length, and nesting depth of accepted payloads (over-limit returns `413`; `screenshot.dataUrl` is bounded separately by `SCREENSHOT_MAX_BYTES`). Lenient defaults (`500` / `20000` / `1000` / `32`) stay on even when unset. When you change `MAX_FIELD_LENGTH`, set the widget's `maxFieldLength` to the same value
- Configurable per-IP fixed-window rate limit via `RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX_CLIENTS` (or config `rateLimitMax` / `rateLimitWindowMs` / `rateLimitMaxClients`): defaults to `120` requests per `60000` ms; over-limit returns `429` with `Retry-After`. The client is identified by the socket remote address; behind a reverse proxy, set `RECEIVER_TRUST_PROXY=1` to use the first `X-Forwarded-For` entry instead (off by default so a direct client can't spoof its identity)
- New feedback is rejected with `507` once `MAX_FEEDBACK_COUNT` (or config `maxFeedbackCount`, default `100000`) is reached. Imports count only new unique ids toward this limit, excluding stored ids and duplicates within the bundle. A screenshot write is rejected with `507` once it would exceed `SCREENSHOT_DISK_MAX_BYTES` (or config `screenshotDiskMaxBytes`, default `500000000`). Disk usage is measured once at startup and tracked on save/delete
- Setting `RECEIVER_TOKEN` (or config `receiverToken`) requires auth on the operation endpoints (`POST /import` / `POST /feedback/:id/status` / `DELETE /feedback/:id` / `POST /feedback/:id/github-issue`) and the read endpoints (`GET /` (inbox) / `GET /feedback.json` / `GET /screenshots/:file`). API clients send `Authorization: Bearer <token>`; browsers enter the same token in the inbox login form (`GET /login`). After login, the session is held in an HMAC-derived HttpOnly cookie (7-day expiry, `SameSite=Lax`, `Secure` when `publicBaseUrl` is `https://`) — the raw token is never stored in the browser, and rotating the token invalidates every session at once. When unset, local runs work without auth (the widget's `POST /feedback` and `GET /widget.js` stay public even when set; the widget's status lookup `POST /feedback-status` goes away when set, by default)
- `STATUS_LOOKUP` (or config `statusLookup`) decides whether the widget's status lookup `POST /feedback-status` is open. When unset (`null` in config), it is open only without `RECEIVER_TOKEN`. `1` / `true` opens it even with a token (for a receiver that keeps a token on its inbox but is only used locally; anyone who can reach it and knows a feedback id can read its status, so startup logs a warning). `0` / `false` always closes it
- `LOG_COMMENTS` (or config `logComments`) set to `1` / `true` puts the first 60 characters of each comment into the received / imported log lines (`received feedback` / `imported feedback`). It defaults to `false`, and the log then shows only the feedback id and the outcome (a log can travel further than the inbox, such as a terminal's scrollback or the host's log service). The startup line `comment log:` shows the current setting
- Setting `INGEST_KEYS` (comma-separated env) or config `ingestKeys` (array) requires a matching `X-PatchLoop-Ingest-Key` header on widget posts (`POST /feedback`); a missing or wrong key returns `401`. Config entries can be `"key"` strings or `{ "key": "...", "projectId": "..." }` objects that **bind a key to a projectId**: posts with a bound key are refused with `403` when the payload's `projectId` differs from the key's, and get the key's projectId filled in when the payload has no `projectId` (or `null`, as when posting through the API directly). The widget always sends a `projectId` (default `local-demo`), so with a bound key, pass the same `projectId` in the widget's init too. Keys are public — they ship inside the demo page — so this is not secret-based auth (it identifies the project, deters indiscriminate spam, and can be rotated to revoke). When unset, anyone can post as before
- Setting `ALLOWED_ORIGINS` (comma-separated env, or config `allowedOrigins` array) restricts CORS for widget posts and status lookups (`POST /feedback` / `POST /feedback-status`) to the listed origins (exact `scheme://host[:port]` match). JSON POSTs trigger a browser preflight, and the receiver also rejects posts carrying an unlisted `Origin` with 403. CLI/API posts without `Origin` remain supported (ingest keys are configured separately). When unset, every origin is allowed (`*`) as before, with a startup log warning. CORS headers are only emitted on `POST /feedback` and `POST /feedback-status`; the inbox, operation endpoints, and screenshots are same-origin surfaces and return no CORS headers at all (a second wall next to auth). Received feedback records `received: { origin, originAllowed }`, visible in the inbox raw payload (the Origin header is spoofable, so treat it as a hint)
- JSON mutations (`POST /feedback`, `POST /import`, status updates, and GitHub issue creation) require `Content-Type: application/json` (an optional charset is supported). Send `{}` even for an otherwise empty GitHub creation request. Missing or other media types return 415. Live posts start with status `new`; receipt time, integration results, and delivery history are assigned by the receiver.
- Forwards received feedback to a Slack Incoming Webhook when `SLACK_WEBHOOK_URL` is set
- Configurable Slack screenshot presentation via `SLACK_IMAGE_MODE` (`auto` / `link` / `block` / `upload` / `off`)
- Optional Slack file upload via `SLACK_BOT_TOKEN` and `SLACK_UPLOAD_CHANNEL_ID`
- Configurable Slack forwarding timeout via `SLACK_TIMEOUT_MS` (default `5000`)

`examples/plain-html/` is preconfigured to send to `http://localhost:4000/feedback`. Serve the page with `python3 -m http.server 4173`, start the receiver alongside it, and submitted comments will appear in the inbox.

### Keeping And Deleting Data

There is no automatic retention yet. Delete data you no longer need by hand, wherever it is:

- Feedback in the inbox: the card's delete button (`DELETE /feedback/:id`) removes the feedback and its screenshot
- All receiver data: stop the receiver, then delete the sqlite DB (`FEEDBACK_DB_PATH`) and the screenshot directory (`SCREENSHOT_DIR`). A legacy `feedback.json` (`FEEDBACK_STORE_PATH`) and the backups next to it, `feedback.json.migrated-*` / `feedback.json.corrupt-*`, hold feedback too (sometimes with screenshot data); delete them if present (a legacy `feedback.json` left behind with the DB gone is imported again on the next start)
- Export files you received (`*.patchloop-feedback.json`): they stay where you saved them after the import; delete them when no longer needed. They include screenshots
- What the browser keeps: the widget panel's “この端末のコメントを消す” removes the open page's comments. To remove the other pages of the same project / demo, the reviewer name and the display setting too, clear the site's data (localStorage) in the browser
- What left the receiver (Slack notifications, GitHub Issues): deleting in the receiver does not remove them; delete them in each service
- The receiver log: comment text stays out of it by default (`LOG_COMMENTS`). Feedback ids and outcomes are logged, so a log service keeps them as long as its own retention says

### Receiver Config File

Local settings such as the Slack webhook URL can live in `server/receiver.config.json`. This file is ignored by git. A shareable template is available at `server/receiver.config.example.json`.

```sh
cp server/receiver.config.example.json server/receiver.config.json
```

```json
{
  "host": "127.0.0.1",
  "port": 4000,
  "feedbackDbPath": "feedback.db",
  "screenshotDir": "screenshots",
  "publicBaseUrl": "http://127.0.0.1:4000",
  "maxBodyBytes": 3000000,
  "screenshotMaxBytes": 1500000,
  "slackWebhookUrl": "https://hooks.slack.com/services/...",
  "slackImageMode": "auto",
  "slackBotToken": "",
  "slackUploadChannelId": "",
  "slackTimeoutMs": 5000
}
```

Relative path values such as `feedbackDbPath` and `screenshotDir` are resolved from the config file location. See `server/receiver.config.example.json` for the full list of supported keys and their defaults (`feedbackStorePath` is the legacy `feedback.json` migration source and normally does not need to be set). `publicBaseUrl` is used for screenshot links and image blocks in Slack messages. For local testing, `http://127.0.0.1:4000` is enough. If you want Slack image previews to render outside your machine, point it at a public tunnel such as ngrok.

`slackImageMode` defaults to `auto`. When `publicBaseUrl` is public, the receiver adds a Slack image block. When `slackBotToken` and `slackUploadChannelId` are also set, the receiver uploads the saved screenshot as a Slack file through the Slack Web API. The token needs the Slack App `files:write` scope. Use `link` for links only, `block` to force an image block, `upload` for file upload only, or `off` to omit screenshot presentation.

To use a config file from another path, run `PATCHLOOP_RECEIVER_CONFIG=/path/to/receiver.config.json node server/receive.js`.

Invalid numeric settings (non-numeric values, or 0 / negative / fractional values for the limit-style settings, `SLACK_TIMEOUT_MS` / `slackTimeoutMs`, and `GITHUB_TIMEOUT_MS` / `githubTimeoutMs`) are ignored in favor of the default (an invalid env value falls back to the config value) with an `ignored invalid setting ...` warning in the startup log. Timeouts accept only positive integers and default to `5000` ms for Slack and `8000` ms for GitHub. The effective values are printed in the startup `limits:` / `rate limit:` / `timeouts:` summary lines.

`RECEIVER_TRUST_PROXY` / `trustProxy`, `STATUS_LOOKUP` / `statusLookup`, `SLACK_IMAGE_MODE` / `slackImageMode`, `GITHUB_REPO` / `githubRepo`, and `LOG_COMMENTS` / `logComments` also warn on invalid values and use a valid value in env → config → default order. Empty or whitespace-only values count as unset, so an empty env value does not override the config. Booleans accept `1` / `true` / `yes` / `on` and `0` / `false` / `no` / `off` (ignoring case and surrounding whitespace), as well as JSON `true` / `false` in config. Image modes are `auto` / `link` / `block` / `upload` / `off`; repositories use the `owner/name` form. The respective defaults are `false`, enabled only without `RECEIVER_TOKEN`, `auto`, empty (GitHub Issue creation disabled), and `false`.

Environment variables override the config file. For example, to try Slack forwarding temporarily:

```sh
SLACK_WEBHOOK_URL="https://hooks.slack.com/services/..." node server/receive.js
```

If Slack forwarding fails, the receiver still stores the payload. The Slack result is visible in the saved payload under `integrations.slack` and in the inbox `Slack` row. Screenshot `dataUrl` values are saved as files by the receiver and replaced with `screenshot.url` in stored payloads. The internal image file path, `screenshot.path`, stays in storage and is omitted from the JSON API, inbox raw payload, and GitHub issue body.

### Creating GitHub Issues

Feedback in the inbox can be turned into GitHub Issues. Issue creation happens on the receiver; the token never reaches the browser.

```sh
GITHUB_TOKEN="github_pat_..." GITHUB_REPO="owner/repo" node server/receive.js
```

- `GITHUB_TOKEN` / `githubToken` — GitHub token. **A fine-grained PAT scoped to the target repository with Issues: write is recommended**
- `GITHUB_REPO` / `githubRepo` — repository to create issues in (`owner/repo`)
- `GITHUB_LABELS` / `githubLabels` — labels to apply (comma-separated in env, array in config)
- `GITHUB_ASSIGNEES` / `githubAssignees` — assignees (same formats)
- `GITHUB_API_BASE` / `githubApiBase` — API base URL (defaults to `https://api.github.com`; override for GHES or tests)
- `GITHUB_TIMEOUT_MS` / `githubTimeoutMs` — timeout (defaults to `8000`)

When configured, each inbox card shows a “GitHub Issue を作成” (Create GitHub Issue) button. Created issues include the comment, reviewer, page URL, selector, target position, viewport, screenshot link, and the raw payload. The result is persisted as `integrations.github` and the card shows the issue link (or the error on failure). Creating a second issue from the same feedback is rejected. The API equivalent is `POST /feedback/:id/github-issue`.

The screenshot image only renders inside the issue if GitHub can reach your `publicBaseUrl`; with a local receiver the link still works locally. When `RECEIVER_TOKEN` is set, GitHub's image proxy cannot authenticate, so the issue carries only an `[Open screenshot]` link instead of an inline embed (opening it requires signing in to the receiver).

### Public Deployment (EC2 etc.)

The receiver defaults to a local-prototype setup (`127.0.0.1` bind, no auth, CORS `*`). When exposing it to the internet, assume the following:

- **Terminate HTTPS at a reverse proxy (nginx / Caddy / ALB etc.)**: the receiver itself speaks plain HTTP. Behind a proxy, bind `HOST` to an interface only the proxy can reach, and set `RECEIVER_TRUST_PROXY=1` so the rate limiter sees real client IPs
- **Always set `RECEIVER_TOKEN`**: publishing without it exposes the inbox, the feedback data, and every operation endpoint with no auth
- **List your demo page origins in `ALLOWED_ORIGINS`**: restrict widget posts to the origins you expect
- **Set `INGEST_KEYS` and pass `ingestKey` to the widget init**: rejects keyless `POST /feedback` with 401. Keys are public by design, so treat them as leak-tolerant and keep them per-project so they can be rotated
- **Point `PUBLIC_BASE_URL` at your public `https://` URL**: it determines the reachability of screenshot links sent to Slack / GitHub, and the session cookie's `Secure` attribute follows this URL's scheme
- **Inject secrets (`RECEIVER_TOKEN` / `GITHUB_TOKEN` / `SLACK_WEBHOOK_URL` etc.) via env**: env overrides the config file. If you keep them in `receiver.config.json` instead, keep the file out of git and under file-permission control
- **Point liveness monitoring at `GET /healthz`**: it needs no auth, is exempt from rate limiting, and returns 200 / 503 including a store connectivity check. systemd / ALB stops trigger a graceful shutdown via SIGTERM (in-flight requests are drained, so set the stop timeout above 10 seconds)

```sh
RECEIVER_TOKEN="<long-random-token>" \
INGEST_KEYS="<per-project-public-key>" \
ALLOWED_ORIGINS="https://demo.example.com" \
PUBLIC_BASE_URL="https://feedback.example.com" \
RECEIVER_TRUST_PROXY=1 \
HOST=127.0.0.1 PORT=4000 node server/receive.js
```

## Slack Direct Mode

Use `deliveryMode: "slack-webhook"` to send directly from the browser to a Slack Incoming Webhook without running the receiver. When the panel's delivery settings (`showDeliverySettings`) are enabled, you can switch the target to `Slack に直接送信（結果確認不可）` and enter the webhook URL in the UI.

```js
window.PatchLoop.init({
  deliveryMode: "slack-webhook",
  slackWebhookUrl: "https://hooks.slack.com/services/..."
});
```

This exposes the webhook URL in the browser, so keep it to disposable testing webhooks in public environments. Incoming Webhooks cannot send a browser-generated `dataUrl` screenshot as a Slack image or file, so Slack direct mode sends the comment, page, target position, selector, viewport, and screenshot capture status. The screenshot data still remains available in the widget payload and `onSubmit`. To show or upload the generated screenshot in Slack, use receiver mode with `publicBaseUrl` or Slack file upload settings. Direct browser delivery uses `no-cors`, so the response body is not available to the widget.

## Download Mode And Receiver Import

Use `deliveryMode: "download"` to save feedback as a local file without running the receiver or using a Slack webhook.

```js
window.PatchLoop.init({
  deliveryMode: "download",
  showDeliverySettings: true
});
```

In download mode, comments collect in the panel. “未送信を書き出す（N）” exports **all unexported comments in one JSON file** named `<project>-<demo>-<count>-<timestamp>.patchloop-feedback.json`. “書き出し済み” records that a download started, not that the file was saved or imported. Use “全件を再ダウンロード” to download everything again. Both take the comments saved on this device by every page with the same `projectId` / `demoId`, so there is no need to export page by page (with `persistFeedback: false`, only the open page's comments). When other pages have unexported comments, the panel shows how many. The exported marks are saved with each page's data. Another page left open in another tab keeps them, except on comments edited in that tab. A comment edited after its export goes into the next export as a revision with a new ID, so an import does not skip it as a duplicate. The bundle is a versioned JSON file with a `feedback` array.

```json
{
  "kind": "patchloop-feedback-bundle",
  "version": 2,
  "exportedAt": "2026-06-16T00:00:00.000Z",
  "projectId": "patchloop",
  "demoId": "plain-html-renewal-review",
  "feedback": [
    {
      "id": "pl_...",
      "screenshot": {
        "status": "captured",
        "dataUrl": "data:image/svg+xml;base64,..."
      }
    }
  ]
}
```

To import a bundle, start the receiver and open the inbox (`http://127.0.0.1:4000/`), then choose the `.patchloop-feedback.json` file in the “ファイルを読み込む” (Load a file) panel (the panel is collapsed when the inbox already has feedback). Each request is capped by `MAX_BODY_BYTES` (3,000,000 bytes by default), so a file with many screenshot comments goes over it. The inbox's “ファイルを読み込む” splits a file over the cap into parts that fit `MAX_BODY_BYTES` and `MAX_IMPORT_ITEMS` and sends them oldest comments first (the inbox ends up in the same order as one request would leave it). The receiver checks each part on its own, so only a part holding an invalid comment is left out and counted as failed (sent as one request, the whole file would be refused). If it stops part way, importing the same file again on the same page goes on from where it stopped (after a page reload it starts over, and what was already added is skipped as duplicates). A single comment over the cap (or the comments sharing one id, which go together) cannot be imported; the inbox says how to raise the cap. A file with a `createdAt` that is not ISO 8601 with a time zone is sent whole, since the receiver could read such a date, and so the order, differently (the widget always writes the time zone). To import through the API, post the same JSON to `POST /import`; it goes as one request, so a file over the cap gets `413`.

```sh
curl -X POST http://127.0.0.1:4000/import \
  -H "Content-Type: application/json" \
  --data-binary @patchloop-feedback.json
```

The receiver validates the bundle version (both the single-feedback v1 and the array-based v2 batch) and payload shape, saves each feedback's screenshot `dataUrl` to `server/screenshots/`, and appends the imported feedback to the store. Imported feedback gets `source: "import"` and `importedAt`. A valid triage `status` (`new` / `accepted` / `fixed` / `ignored`) is kept, a missing one becomes `new`, and any other value rejects the whole batch with 400. For a batch import, ids that already exist are skipped as duplicates (the rest still land), and the response returns `imported`, `duplicates`, and `failed`. If any payload in the bundle is invalid, the whole batch is rejected with 400 and nothing is written. The receiver does not forward imported feedback to Slack; the inbox shows `Slack: skipped`.

After attempting each save, the response is `201` if at least one item was imported, including partial failures. If none were imported and saves failed, it is `507` when every failure is a storage capacity limit, or `500` otherwise. Save failures take priority over duplicates; duplicates alone return `409`. All these responses include the summary fields such as `imported`, `ids`, `duplicates`, and `failed`. Each `failed` entry contains `id`, `error`, and the cause's `status` (`507` for capacity limits, `500` for database or file write errors, etc.). The inbox also explains capacity limits or receiver save errors. Capacity limits can be changed through receiver settings such as `screenshotDiskMaxBytes` / `SCREENSHOT_DISK_MAX_BYTES`. Whole-batch rejections before saving, such as validation errors (`400` / `413`) or the feedback count limit (`507`), continue to return `error`.

## Current Boundary

GitHub Issue creation is a manual action from the receiver inbox only; there is no automatic creation or two-way sync. Slack support is currently a local-receiver Incoming Webhook prototype. The local receiver persists received feedback in SQLite. The widget feedback list can be persisted in browser `localStorage`. Team user and permission management, scheduled backups, and retention management are not implemented. Use a receiver `endpoint` or download mode when you need to collect feedback outside the current browser.

Not included yet:

- Slack App / OAuth integration
- Team user and permission management, scheduled backups, and retention management
- Pixel-perfect browser screenshot capture (see "What Screenshots Do Not Capture" for what is missing)
- Full isolation from page CSS (page rules on bare element names, `*`, `::before` and `::after` no longer reach the widget, but rules of specificity (0,1,1) or higher such as `button:hover`, `!important`, attribute rules loaded after the widget starts, rules on other pseudo-elements (`::placeholder`, `::marker`, `::selection` and so on), and `direction` / `unicode-bidi`, which `all` does not reset, still can. To hide the widget with page CSS, use `!important` or a selector such as `body [data-patchloop-root]`)
- Per-reviewer authentication (the ingest key is a per-project public key and does not identify individuals; signed tokens issued behind a demo-side login are future scope)
- AI PR integration
- Checks on browsers other than desktop Chrome / Edge, and selecting areas by touch or keyboard alone (see "Supported Environments")
